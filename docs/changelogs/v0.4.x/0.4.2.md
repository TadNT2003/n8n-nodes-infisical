# Changelog — 0.4.2

_Compared against 0.4.1._

This release adds a new **Identity** resource for managing Infisical machine identities and their Universal Auth configuration directly from n8n, extends the **Project** resource with identity-to-project membership management, and fixes a JSON-mode validation bug in **InfisicalSync** that rejected 16 OAuth2 credential types.

## Highlights

- **New `Identity` resource** — machine identity CRUD, Universal Auth attach/get/update/revoke, and Universal Auth client secret create/list/revoke (12 operations total).
- **`Project` resource gains identity membership management** — Add, Get, Get Many, Update, and Remove Identity Membership.
- **InfisicalSync — fixed JSON-mode validation** for 16 OAuth2 credential types that previously failed with "Credential validation failed" errors.
- **InfisicalSync — corrected OAuth safety guidance** in the node UI: the access-token wipe risk is now correctly attributed to Update Strategy rather than to OAuth Credential Handling.
- **Internal** — deduplicated the credential test method shared by both nodes.

## Infisical node — new resource & operations

### Identity (new resource)

| Operation | Method | API endpoint |
| --- | --- | --- |
| **Create** | `POST` | `/v1/identities` |
| **Get** | `GET` | `/v1/identities/{id}` |
| **Get Many** | `GET` | `/v1/identities?orgId={orgId}` |
| **Update** | `PATCH` | `/v1/identities/{id}` |
| **Delete** | `DELETE` | `/v1/identities/{id}` |
| **Attach Universal Auth** | `POST` | `/v1/auth/universal-auth/identities/{id}` |
| **Get Universal Auth** | `GET` | `/v1/auth/universal-auth/identities/{id}` |
| **Update Universal Auth** | `PATCH` | `/v1/auth/universal-auth/identities/{id}` |
| **Revoke Universal Auth** | `DELETE` | `/v1/auth/universal-auth/identities/{id}` |
| **Create Client Secret** | `POST` | `/v1/auth/universal-auth/identities/{id}/client-secrets` |
| **List Client Secrets** | `GET` | `/v1/auth/universal-auth/identities/{id}/client-secrets` |
| **Revoke Client Secret** | `POST` | `/v1/auth/universal-auth/identities/{id}/client-secrets/{clientSecretId}/revoke` |

Identities are organization-scoped machine identities (Create/Update support metadata and delete protection; Create requires an Organization ID and Name). Universal Auth attach/update accept access-token TTL/max-TTL/num-uses-limit/period and optional client-secret/access-token trusted IP ranges.

> **Infisical API quirk:** the Revoke Client Secret endpoint returns a 500 error if no JSON body is sent at all, even though every field it accepts is optional. This node always sends `{}` defensively to work around it.

### Project — new identity membership operations

| Operation | Method | API endpoint |
| --- | --- | --- |
| **Add Identity Membership** | `POST` | `/v1/projects/{projectId}/memberships/identities/{identityId}` |
| **Get Identity Membership** | `GET` | `/v1/projects/{projectId}/memberships/identities/{identityId}` |
| **Get Identity Memberships** | `GET` | `/v1/projects/{projectId}/memberships/identities` |
| **Update Identity Membership** | `PATCH` | `/v1/projects/{projectId}/memberships/identities/{identityId}` |
| **Remove Identity Membership** | `DELETE` | `/v1/projects/{projectId}/memberships/identities/{identityId}` |

Add and Update accept one or more **Roles** — a built-in role slug (`admin`/`member`/`viewer`/`no-access`) or a custom project role slug — each optionally time-bound via Is Temporary, Temporary Mode, Temporary Range, and Temporary Access Start Time.

> **Note:** org "admin" role does not imply project membership. An identity must actually be a member of a project (with a role that grants it) before it can manage that project's secrets or other identities' memberships — see the Compatibility notes below.

## InfisicalSync — fixes

### JSON-mode validation no longer rejects hidden OAuth2 fields

Several OAuth2 credential types share a base schema with fields n8n never exposes in any UI (e.g. `serverUrl`, `sendAdditionalBodyProperties`, `additionalBodyProperties`, gated behind an internal `useDynamicClientRegistration`/`grantType` flag that isn't itself exposed either). **Sync to Infisical**'s **JSON mode** validated these as if the user were expected to supply them, so pushing a real exported credential of any of these types failed with a `Credential validation failed` error:

`googleOAuth2Api`, `googleSheetsOAuth2Api`, `googleDriveOAuth2Api`, `googleDocsOAuth2Api`, `slackOAuth2Api`, `microsoftTeamsOAuth2Api`, `twitterOAuth2Api`, `linkedInOAuth2Api`, `discordOAuth2Api`, `salesforceOAuth2Api`, `hubspotOAuth2Api`, `dropboxOAuth2Api`, `spotifyOAuth2Api`, `githubOAuth2Api`, `gitlabOAuth2Api`, `oAuth2Api`.

JSON-mode validation now merges the same schema-derived safe defaults the Infisical → n8n pull path already relies on before checking the user's data — fixing all 16 types generically, and any future type with the same shape, instead of requiring a hardcoded default per type. Form mode was never affected (it already skipped validating fields it doesn't expose).

### OAuth Credential Handling descriptions corrected

The **Update All** option's description previously implied that updating an already-connected OAuth credential always wipes its access token. In fact this only happens under **Update Strategy: Full Replace** — under **Partial Merge** (the default), the token is preserved. The **Create Only** option's description no longer implies the same blanket claim either. Both descriptions, and the parent field's description, now correctly point to **Update Strategy** as the setting that actually determines whether an update can wipe an already-connected credential's access token.

## Internal

- Deduplicated the `testInfisicalApiCredentials` credential test method — previously copy-pasted verbatim in both `Infisical` and `InfisicalSync` — into a shared `utils/credentialTest.ts`.

## Compatibility notes

- **Infisical:** org-level roles (e.g. org "admin") do not grant project-scoped permissions. An identity needs an actual project membership with a sufficient role to manage that project's secrets, folders, or other identities' memberships.
- No new n8n or Infisical version requirements beyond those already listed for 0.4.1.
